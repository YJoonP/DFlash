# DFlash × Qwen3.5-4B — 스마트폰 NPU 에서의 추측 디코딩

> **요약 (English)**
> - **What**: [DFlash](https://github.com/z-lab/dflash) block-diffusion speculative decoding with **Qwen3.5-4B** as the target, run fully on Qualcomm Hexagon NPUs through the ExecuTorch QNN backend: Galaxy S26 Ultra (SM8850) and Galaxy S25 (SM8750).
> - **The hard part**: Qwen3.5 is a hybrid model (24 Gated DeltaNet layers + 8 attention layers). Its recurrent state cannot be rolled back like a KV cache when draft tokens are rejected.
> - **Approach**: the final design *defers and recomputes* the accepted rows inside the next verify call. It is made bit-exact, and its NPU time was recovered by removing every quantization-grid mismatch.
> - **Result (block size 16)**: S26 **58.3 tok/s, 2.90× autoregressive**; S25 **54.7 tok/s, 3.06×**. Recompute, checkpointed recompute and checkpoint-off all produce identical tokens.

이 문서는 2026-10-01 ~ 10-15 에 진행한 "Qwen3.5-4B target + DFlash draft" NPU 이식 작업의 정리입니다. 모든 DFlash 수치는 **b = 16** (검증 1회에 초안 16토큰)입니다.

## 1. 구성

| 항목 | 내용 |
|---|---|
| Target | Qwen/Qwen3.5-4B. 32층 = Gated DeltaNet 24층 + gated full attention 8층 |
| Draft | z-lab/Qwen3.5-4B-DFlash. 블록 16, target 의 8개 층(1, 5, …, 29) hidden state 를 입력으로 씀 |
| 양자화 (target) | 활성값 16bit. 선형층 가중치 4bit(32개 블록 단위), lm_head 8bit. KV cache 8bit. DeltaNet 재귀 상태 16bit |
| 양자화 (draft) | 활성값 16bit, 가중치 4bit(32개 블록 단위) |
| 실행 | ExecuTorch QNN 백엔드(QAIRT 2.49), HTP context binary. target 은 9개 샤드 |
| DeltaNet 연산 | HVX 커스텀 연산(op package). 16bit 정수 상태로 행 단위 델타 규칙 갱신 |
| 기기 | Galaxy S26 Ultra (SM8850, Hexagon v81), Galaxy S25 (SM8750, Hexagon v79) |
| 러너 | MobiSpec.cpp 기반 C++ 러너. zero copy(등록 메모리), 샤드 메모리 고정, NPU 출력의 16bit argmax |

## 2. 문제: DeltaNet 상태는 되돌릴 수 없다

- 어텐션의 KV cache 는 거절된 토큰 위치를 그냥 버리면 됩니다.
- DeltaNet 은 토큰마다 128×128 상태(층당 헤드 32개, 1 MB)를 덮어씁니다. 초안 16토큰을 검증하고 나면, 실제로 받아들인 위치까지만 반영된 상태가 필요합니다.

세 가지 방식을 구현했습니다.

| 방식 | 동작 | 비용 |
|---|---|---|
| **저장 방식** | 검증하면서 16개 위치의 상태를 모두 내보내고, 받아들인 위치의 상태를 골라 씀 | NPU 가 상태 16개를 써야 하고, CPU 쪽에 스냅샷 준비·선택 비용이 듦 |
| **재계산** | 상태는 저장하지 않음. 검증 때 만든 k, v, β, 감쇠, conv 입력("재료")을 넘겨 두었다가, 다음 검증 호출 안에서 받아들인 행만큼 상태를 다시 계산(커밋)함 | 커밋 행 수만큼 NPU 계산 (v5 기준 행당 0.34 ms) |
| **ckpt10** | 재계산 + 검증 연산을 0–9행 / 10–15행 두 조각으로 나누고 10행 시점 상태를 저장. 10개 이상 받아들이면 그 상태에서 이어서 커밋함 | 체크포인트 출력 1 MB × 24층 |

## 3. 정확성: 재계산이 검증과 "같은 계산"이 되게 하기

재계산 결과가 검증 때 상태와 달라지면, 같은 입력에서도 방식에 따라 토큰이 달라집니다. 원인은 비트 수가 아니라 **양자화 눈금**이었습니다.
- 16bit 값을 32bit 로 바꿨다 되돌려도, 같은 눈금(scale, offset)이면 값이 그대로입니다.
- 하지만 보정 단계는 텐서마다 눈금을 따로 정합니다. 그래서 "저장한 눈금"과 "읽는 눈금"이 다른 곳에서 값이 다시 반올림됩니다.

예를 들어 0층 v 는 저장 간격이 0.000342, 읽기 간격이 0.000155 였습니다. 검증 때 3칸(0.001026)이던 값이 다음 호출에서 7칸(0.001085)으로 읽혔습니다.

| 찾은 불일치 | 증상 | 해결 |
|---|---|---|
| 재료 입력 눈금 ≠ 출력 눈금 | 커밋이 반올림된 재료로 상태를 만듦 | 재료 입력을 출력 눈금으로 |
| 재료를 헤드 묶음으로 자를 때 눈금이 또 바뀜 (384곳 중 343곳) | 상태 코드 0.2~0.3% 가 ±1~3 차이 → 체크포인트 켬 ≠ 끔 | 재료 경로 전체를 눈금 하나로 |
| 2개 층(16·21층)의 상태 입력이 1코드 다른 눈금으로 읽힘 | 18개 중 1개 프롬프트에서 켬 ≠ 끔 | 상태 입력을 저장 눈금으로 읽기 |
| ckpt10 에서 자른 쿼리 조각(192개 중 143개)이 따로 보정된 눈금 | ckpt10 ≠ 일반 재계산 | 조각을 원래 묶음 눈금으로 |

검증 방법은 세 가지입니다.
- 같은 토큰열을 강제로 넣는 재생 시험에서 128위치 로짓 지문을 비교했습니다.
- 커밋된 상태를 코드 단위로 비교했습니다.
- 18개 프롬프트의 생성 토큰을 비교했습니다.

**최종본(v5)의 결과**
- 재계산, ckpt10 끔, ckpt10 켬이 18/18 같은 토큰을 냈고, 로짓은 0/128, 상태는 0/524,288 코드가 달랐습니다.
- S26 과 S25 의 토큰도 18/18 같습니다.
- 저장 방식과는 토큰이 다릅니다(2/18 같음). 같은 방식 안에서도 검증 묶음 크기(1/4/16)만 바꾸면 로짓이 평균 약 0.06 달라지기 때문입니다. 그래서 정확성 목표는 "재계산 = ckpt10 켬 = 끔"으로 잡았습니다.

## 4. 속도: 정확성 수정이 늘린 NPU 시간 되찾기

- 정확성 수정을 넣자 S25 에서 검증 1회의 NPU 시간이 약 +9 ms(+13%) 늘었습니다.
- 연산 종류와 개수, 연산 사이클 합은 거의 같았습니다. 복사 제거나 재료 입출력 비트 수와도 무관했습니다.

**원인: 거의 같은 두 눈금이 만나는 곳마다 QNN 이 변환(재양자화) 연산을 넣음**
- conv 창(최근 3행 + 이번 16행)을 저장 방식과 같은 값으로 맞추려고, 창을 conv 상태 눈금으로 저장하고 conv 는 원래 눈금으로 읽게 했습니다.
- 두 눈금은 간격이 100만분의 5 다르고 기준 코드는 같아서 사실상 같은 눈금입니다. 그런데도 DeltaNet 층마다 19행×8192 값을 다시 반올림하는 연산이 생겼습니다.
- 메모리 배치도 바뀌어서, 샤드 0 의 VTCM 넘침 버퍼가 0.8 → 22 MB 로 커졌습니다.

**해결**
- 이 conv 창 수정은 재계산과 ckpt10 의 정확성에는 필요 없었습니다. 두 방식이 conv 를 같은 그래프로 계산하기 때문입니다. 그래서 수정 자체를 뺐습니다(v5).
- 같은 세션에서 비교한 NPU 시간은 이렇습니다.
  - S26 재계산: 71.01 → 67.68 ms
  - S25: 76.31 → 73.55 ms (재계산), 70.47 ms (ckpt10 그래프)
- 커밋 비용도 행당 0.81 → 0.34 ms (S26) 로 줄었습니다.

- **생성**: thinking 채팅 템플릿, greedy, 128토큰
- **순서와 휴식**
  - 설정 순서를 프롬프트마다 돌려 번갈아 쟀습니다.
  - 측정 사이에 60초 이상 쉬고, SoC 38 °C 미만 / 배터리 33 °C 미만일 때 시작했습니다. 시작 시 SoC 는 약 26 °C 였습니다.

- **AL**: 검증 1회당 받아들인 토큰 평균

## 6. 알게 된 것

1. **NPU 시간은 대략 "16토큰 검증 + 커밋 행 수 × 행당 비용"입니다.**
   - S26 v5 는 65.3 ms + 0.34 ms × 행 수입니다.
   - 단계당 평균 5.3행을 커밋하므로 커밋은 약 1.8 ms 입니다.
2. **ckpt10 체크포인트는 이득이 없었습니다.**
   - AL 이 약 5.2 라서 10개 이상 받아들이는 단계가 18~19% 뿐입니다.
   - 정확히 10개를 받아들이면 커밋할 행이 0개가 되는데, 이 경로가 호출당 +23~33 ms 걸려 아낀 시간을 상쇄했습니다.
3. **검증 연산을 두 조각으로 나눈 그래프가 더 빠릅니다.**
   - 체크포인트를 꺼도 S25 −3.1 ms, S26 −0.6 ms 입니다.
   - 계산량은 같아서 원인은 아직 모릅니다.
4. **두 눈금이 만나는 곳은 몇 ppm 차이여도 성능에 큰 영향을 줍니다.** 변환 연산이 들어가고 메모리 배치도 바뀝니다. export 마다 이런 지점을 자동으로 세는 검사를 넣었습니다.
5. **q·k 복제**: 검증·커밋 경로는 q·k 16헤드를 v 헤드 수(32)에 맞춰 복제합니다. 1토큰 디코드 커널은 이미 복제 없이 v 헤드 h 가 k 헤드 h/2 를 읽습니다.

# Qwen3.5-4B DFlash (b = 16) 정확한 재계산 — 개선 경위와 최종 결과

- 작성: 2026-10-16 KST
- 실험 기간: 2026-10-11 ~ 2026-10-15 KST
- 범위
  - 모든 DFlash 수치는 b = 16 입니다. 블록 크기 16 은 검증 1회에 초안 16토큰을 확인한다는 뜻입니다.
  - 시각은 모두 KST 입니다.
- 최종 측정 원본은 부록에 그대로 붙였습니다.

## 1. 목표와 현재 결론

**목표**
1. **같은 결과**: 재계산과 ckpt10(체크포인트 켬/끔)이 같은 방식으로 계산해서 토큰과 AL 이 완전히 같아야 합니다. 재료도 16bit 로 저장하고 같은 16bit 눈금으로 읽습니다.
2. **속도**: 정확성 수정 때문에 늘어난 NPU 시간을 없앱니다. S25 에서 옛 채택 export 보다 +9 ms 늘었던 것이 출발점입니다.

**현재 최종본 = v5 export (S26·S25 둘 다)**
- 재계산, ckpt10 끔, ckpt10 켬 세 방식의 토큰이 18개 프롬프트 모두 같고, AL 은 5.236 입니다.
- S26 기기 재생 시험에서 로짓 0/128, 커밋된 상태 0코드가 달랐습니다.
- S25 와 S26 의 v5 토큰도 18/18 같습니다.

| 기기 | AR | 저장 방식 | 재계산 v5 | ckpt10 v5 끔 | ckpt10 v5 켬 |
|---|---|---|---|---|---|
| S26 TPS (tok/s) | 20.07 | 50.73 ¹ | 58.02 | 58.20 | **58.27** (2.90×) |
| S25 TPS (tok/s) | 17.89 ² | 46.42 | 53.13 | 54.73 | **54.74** (3.06×) |

² S25 AR 은 10-05 측정값입니다.

**아직 남은 것**
- S25 에서 재계산 v5 는 옛 채택(정확성 수정 없음)보다 NPU 가 +5.2 ms 느립니다. ckpt10 v5 그래프는 +2.1 ms 입니다.
- ckpt10 의 체크포인트는 켜도 이득이 없습니다(4.2절).

## 2. 용어

| 용어 | 뜻 |
|---|---|
| 저장 방식 (S16) | 검증하면서 16개 위치의 DeltaNet 상태를 모두 저장해 두고, 받아들인 위치의 상태를 골라 씀 |
| 재계산 (R16) | 상태를 저장하지 않음. 다음 검증 호출 안에서 지난번에 받아들인 행만큼 상태를 다시 계산(커밋)함 |
| 재료 | 재계산(커밋)에 필요해서 다음 호출로 넘기는 값: k, v, β, 감쇠, conv 입력 x |
| ckpt10 (K16) | 재계산 + 검증의 DeltaNet 연산을 0–9행과 10–15행 두 조각으로 나누고, 10행까지 반영한 상태를 체크포인트로 저장. 10개 이상 받아들이면 그 상태에서 이어서 커밋함 (켬). 끔은 같은 그래프에서 체크포인트를 안 씀 |
| 눈금 (인코딩) | 16bit 양자화의 간격(scale)과 기준 코드(offset). 텐서마다 보정 단계에서 따로 정해짐 |
| 두 눈금이 만나는 곳 | 저장한 눈금과 읽는 눈금이 다른 곳. 값이 다시 반올림되고, QNN 이 변환 연산을 넣음 |
| AL | 검증 1회당 받아들인 토큰 수 평균 |
| NPU 순수 계산 | QNN 이벤트 3012(NPU 실행, 자원 대기 제외)를 9개 샤드에 대해 합한 값. 커밋 + 16토큰 검증 + 그래프 안 입출력이 들어 있음 |
| 샤드 | 모델을 나눈 9개 그래프. 0 = 0–1층, 1–7 = 4층씩(DeltaNet 3 + 어텐션 1), 8 = 30–31층 + lm_head |

### 3.2 정확성: 무엇이 문제였고 어떻게 고쳤나

**핵심은 비트 수가 아니라 눈금이었습니다.** 같은 눈금이면 16bit → 32bit → 16bit 로 바꿔도 값이 그대로입니다. 결과가 달라진 곳은 모두 "저장할 때와 읽을 때 서로 다른 16bit 눈금"을 쓴 곳이었습니다. 보정 단계가 텐서마다 눈금을 따로 정했기 때문입니다.

0층 v 의 실제 값으로 예를 들면 이렇습니다.
- 저장 눈금은 간격 0.000342, 읽기 눈금은 간격 0.000155 였습니다.
- 검증 때 v = 저장 눈금 3칸 = 0.001026 이었습니다.
- 다음 호출에서 읽기 눈금으로 다시 반올림하면 0.001026 ÷ 0.000155 = 6.62칸 → 7칸 = 0.001085 가 됩니다.
- 그래서 커밋은 검증과 다른 v 로 상태를 만들었습니다.

| 찾은 원인 | 증상 | 수정 (export 스위치) |
|---|---|---|
| 재료 입력 눈금 ≠ 재료 출력 눈금 | 커밋이 반올림된 재료로 상태를 만듦 | 재료 입력 = 출력 눈금 (`QNN_DEFER_EXACT=1`, exact v1) |
| 재료 → 헤드 묶음으로 자를 때 눈금이 또 바뀜 (384곳 중 343곳) | 검증 경로와 재생 경로의 반올림이 달라 상태 코드 0.2~0.3% 가 ±1~3 다름 → ckpt10 켬≠끔 | 재료 경로 전체 한 눈금 (`QNN_DEFER_EXACT_ONE_ENC=1`) |
| 16·21층 상태 입력을 읽는 눈금이 저장 눈금과 1코드 차이 (예: offset 22049 vs 22048) | 켬≠끔이 1/18 남음 (프롬프트 243) | 상태 입력을 저장 눈금으로 읽기 (`QNN_STATE_IO_FROM_Q=1`) |
| ckpt10 의 쿼리를 0–9 / 10–15행으로 자른 조각이 따로 보정된 눈금 (192개 중 143개) | ckpt10 끔 ≠ 일반 재계산 | 조각을 원래 묶음 눈금으로 (`QNN_DEFER_SPLIT_Q_ON_GROUP=1`) |

- 검증 방법은 세 가지였습니다.
  - 프롬프트 81 의 AR 토큰을 강제로 넣는 재생 시험에서 위치별 로짓 지문을 비교했습니다.
  - 커밋된 상태를 덤프해 코드 단위로 비교했습니다.
  - 18개 프롬프트의 토큰을 비교했습니다.
- export 마다 정적 검사를 했습니다.
  - `check_v3.py`: S1~S4 엄격 검사
  - `check_exact(_ckpt).py`
  - `check_og.py`: 두 눈금이 만나는 곳 목록
- **저장 방식과는 토큰이 같아지지 않습니다.** 같은 방법 안에서도 검증 묶음 크기(1/4/16)만 바꾸면 로짓이 평균 약 0.06 달라집니다(128위치 중 127곳). 저장 방식과 재계산 v5 의 토큰은 18개 중 2개만 같습니다. 그래서 정확성 목표는 "재계산 = ckpt10 켬 = 끔"입니다.

### 3.3 속도: 왜 NPU 시간이 늘었고 어떻게 줄였나

**증상 (S25 10-13 ab3, 6개 프롬프트)**
- NPU 시간은 옛 채택 69.67, exact conv 78.74, 같은 export 를 재료 32bit 입출력으로 바꾼 것 78.62 ms 였습니다.
- 늘어난 시간은 전부 NPU 안에 있었습니다. 복사 제거(zero copy)는 세 모델 모두 적용돼 있었습니다.
- 두 그래프는 연산 종류와 개수(샤드 1 기준 624개)가 똑같았고, 연산 사이클 합도 ±1% 로 같았습니다. 그런데 시간은 11% 더 걸렸습니다.

**확인한 것**
- 정확성 수정 말고는 옛 채택과 차이가 없었습니다.
  - 보정 데이터가 같은 파일입니다.
  - 컴파일 백엔드가 같은 빌드입니다.
  - 커스텀 연산 등록 정보(스레드 수, 메모리 위치)가 같습니다.
- 재료 입출력을 16bit 로 하든 32bit 로 하든 차이가 없었습니다.
- 연산별 실제 시간을 보려고 QNN linting 프로파일을 켜자 S25 의 NPU(cDSP)가 첫 실행에서 멈췄습니다(오류 0x2301, 스스로 복구됨). 컨텍스트를 만들 때 켜야 하는 기능으로 보입니다.
- 상세(DETAILED) 프로파일은 연산별 사이클만 주고 실제 시간(µs)은 주지 않습니다.

**원인: 거의 같은 두 눈금이 만나는 곳마다 QNN 이 변환 연산을 넣음**
- exact conv export 에는 이런 곳이 46곳 있었습니다.
  - conv 창 24곳 (DeltaNet 층마다, 19행 × 8192)
  - 어텐션 K/V 이어붙이기 16곳
  - 상태 입력 6곳 (16·21층)
- 예를 들어 4층 conv 창은 저장 간격 0.0005449663, 읽기 간격 0.0005449633 으로 100만분의 5 차이이고 기준 코드는 38190 으로 같습니다. 사실상 같은 눈금인데도 층마다 15만 개 값을 다시 반올림했습니다. 연산 하나에 0.42 M 사이클, 24층 합 +10 M 사이클입니다.
- conv 창 수정은 컴파일러의 메모리 배치도 바꿨습니다. 샤드 0 의 VTCM 넘침 버퍼가 0.8 → 22 MB 로 커졌고, 샤드마다 연산 데이터가 +0.2 MB, 상수가 +0.35 MB 늘었습니다.

**수정**
- **v4 (S25)**: conv 가 저장 눈금으로 읽게 해서 변환 연산만 없앴습니다. NPU 79.44 → 75.92 (−3.5 ms) 였지만 큰 넘침 버퍼는 남았습니다.
- **v5**: conv 창 수정 자체를 뺐습니다.
  - conv 창 수정은 재계산의 conv 값을 저장 방식과 똑같이 만들려던 것이었습니다.
  - 재계산과 ckpt10 은 conv 부분을 같은 그래프로 계산하므로, 이 수정이 없어도 둘의 정확성은 유지됩니다(검증 결과 18/18).
  - 그 결과 변환 연산과 큰 넘침 버퍼가 함께 없어졌습니다. 샤드 0 넘침 버퍼는 1.3 MB 이고, 연산 데이터와 상수도 옛 채택 수준입니다.
  - 남은 두 눈금 지점은 40곳입니다. 옛 채택에도 있는 conv 상태 3행 변환 24곳과 어텐션 16곳입니다.
- **효과 (같은 세션)**
  - S26: v3 71.01 → v5 67.68 ms (−3.3). ckpt10 그래프는 70.86 → 67.12 (−3.7) 입니다.
  - 줄어든 시간의 대부분은 커밋 쪽입니다. 커밋 행당 비용이 0.81 → 0.34 ms 로 줄었고(약 −2.5 ms), 16토큰 검증 부분은 66.7 → 65.3 ms (−1.4) 줄었습니다.
  - S25: exact conv 76.31 → v5 73.55 (−2.8), ckpt10 v5 그래프 70.47 (−5.8) 입니다. 옛 채택 68.36 보다는 아직 +5.2 / +2.1 ms 느립니다.

## 5. 다음 방향을 정할 때 필요한 사실

1. **NPU 시간 구성 (v5)**
   - 대략 "16토큰 검증 + 커밋 행 수 × 행당 비용"입니다.
   - S26 은 65.3 + 0.34 × 행 수, S25 는 약 69 + 0.25~0.33 × 행 수 (ms) 입니다.
   - 단계당 커밋은 평균 5.3행이므로 약 1.8 ms 이고, NPU 시간의 3% 정도입니다.
2. **ckpt10 체크포인트는 이득이 없습니다 (켬 ≈ 끔).**
   - 10개 이상 받아들인 생성 단계가 18~19% 뿐입니다. 아낀 시간은 단계당 −0.64 ms (S26) 입니다.
   - 정확히 10개를 받아들이면 커밋할 행이 0개가 되는데, 이때 커널의 "행 없음" 경로(상태 전체 복사로 보임)가 호출당 +33 ms (S26) / +23 ms (S25) 걸립니다. 이 손해가 단계당 +0.68 ms 로 이득을 상쇄합니다.
   - 행이 항상 16개인 프롬프트 처리 단계에서는 효과가 보입니다. S26 v5 기준 72.3 → 68.8 ms 입니다.
3. **검증 연산을 둘로 나눈 ckpt10 그래프가 일반 재계산 그래프보다 빠릅니다.**
   - 체크포인트를 꺼도 S25 −3.1 ms, S26 −0.56 ms 입니다.
   - 계산량도, 동시에 돌 수 있는 단위(헤드 4묶음)도 같아서 이유는 아직 모릅니다.
   - 나누면서 생긴 부담은 NPU 밖 호출 처리 약 +0.2 ms 이고, NPU 안의 부담은 따로 측정하지 못했습니다.
4. **두 눈금 지점이 성능에 큰 영향을 줍니다.**
   - 간격이 몇 ppm 만 달라도 QNN 은 변환 연산을 넣고, 메모리 배치도 바뀔 수 있습니다.
   - 새 export 를 만들면 `check_og.py` 로 conv 창·상태 입력 지점이 0인지 확인합니다.
5. **k 복제**
   - 검증·커밋 경로는 q·k(16헤드)를 32헤드로 복제한 뒤 정규화합니다. 다음 호출로 넘기는 재료 k 도 32헤드 복사본입니다(호출당 3 MiB, 재료 약 12 MiB 중).
   - 토큰 1개짜리 디코드 전용 커널은 이미 v 헤드 h 가 k 헤드 h/2 를 읽는 방식입니다. 09-11 AR 디코드 최적화 때 디코드에만 넣었습니다.
6. **러너는 토큰을 바꾸지 않습니다.** 방법끼리 AL 이 다른 것은 계산 차이 때문입니다.
7. **프로파일 도구의 한계**: linting 은 지금 컨텍스트에서 쓸 수 없고, DETAILED 는 연산별 사이클만 줍니다. 실제 시간은 세션 비교로만 봅니다.
